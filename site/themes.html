Themes

Guardrails people own

Agents are trusted through guardrails that people own (rules that check their output, scoped access, and a firewall on what goes in and what they do) rather than by people reading what they produce.

Ankit Jain mines years of review comments into rules with owners and turns some into deterministic checks, so people own the rules instead of the code. Karan Vaidya gives agents broad but granular access to each app and puts a firewall on both their inputs and their actions. Utkarsh Shrivastava has Netflix's domain teams run a regression eval suite in CI before any new connector or model change, and scales the gate with the stakes, from reads to irreversible writes. All three replace line-by-line supervision with controls a named person or team maintains. Mihail Eric goes further for vertical AI: there is no absolute correctness, so in-house domain experts define what good looks like and evaluations follow them. Lauren Tan puts the most weight on it: on the Grok Bot team every correction to an agent becomes a lint rule, a banned API or a better design, prose rules come last, and code review has shrunk to reading verification artifacts (videos, screenshots, model checks), which is what lets hundreds of pull requests a day land. Overcut gives each narrow agent only the tools and permissions it needs, adds human approval gates where the team wants them, and keeps a full audit trail. Mixedbread carries each document's access rules into the index and makes every search name its user. Ramp attaches the whole agent session to a pull request, so a reviewer checks evidence instead of reading the diff. Steve Yegge's counter-point: an agent yelled at with too many rules fences itself in until nothing gets done. On Nov 12, Michael Liendo (Auth0) scales human-in-the-loop with the stakes: scoped, short-lived credentials from a token store, step-up permissions when a task needs more, out-of-band CIBA approval for high-stakes actions, and virtual cards with limits instead of the real card. Walden Yan's Cognition has agents test in local VMs and send back videos as proof, and Arsalan Bashir (Sentry) gives the agent a cheap deterministic check, such as a dry-run query, so it can iterate and users can trust the result.

Context for AI

AI does its best work on context people have already curated (the intent captured in a session, modeled data, a map of the database), not on raw systems.

George Fraser's companies connect their agents to the same modeled data stack that serves BI, simplify messy data for them, and give them an agent schema as a map. Ankit Jain captures a change's intent and acceptance criteria from the agent session rather than writing specs. Utkarsh Shrivastava calls the AI tool the tip of the iceberg and puts Netflix's lasting investment in the company context beneath it: enterprise skills and MCP servers. In each, the useful input is something a person already shaped. Mihail Eric seeds Monaco's agent memory from sales emails, call transcripts and onboarding context, then promotes what the agents learn back into it. Lauren Tan makes the same point about code: the codebase is the agent's largest input, so whatever patterns it holds, good or bad, are what the next agent copies, and it has to be kept pristine. Aamir Shakir (Mixedbread) puts it as a bottleneck: getting the right data in front of the agent matters more than intelligence. Overcut feeds only the best-scored memories from past runs back as context. Steve Yegge qualifies it: agents never delete, so curated context decays into a garbage dump unless someone prunes it.

Decision load

As agents take over the work, the decisions left to people become the scarce, tiring part, so teams record them, queue them for a person, and keep them few enough to make well.

Across the talks, agents do more of the doing and people are left with the deciding. Ankit Jain finds that human review comments were mostly about decisions and has agents argue so the decisions surface and get written down. Karan Vaidya's security agents queue uncertain findings for a person to judge in the morning. Scott Tolinski's survey shows the cost: running many agents multiplies the decisions and wears people out, and fewer agents in parallel helps. Michelle Chen argues the other way: Cloudflare's Clef decision model lets an agent make the call itself, without minutes of LLM reasoning or a human in the loop, so it can run around the clock. Steve Yegge finds the more agents he deploys, the more humans he needs, and Simon Willison that the job feels harder because the easy part is handled: it doesn't get easier, you just get faster. Cognition's Android-parity agent ran 44 days with almost no human messages, escalating only the key decisions.

Fuel

Token cost is becoming the constraint that separates agent designs: the same answer can cost several times more depending on the harness, the model and how much the agent has to check.

Steve Yegge calls every problem a fuel problem: his factory runs on 22 subsidized Max accounts that would cost about $1.5M a year at API prices, and agents that don't trust their environment spend tokens checking it. Philipp Schmid finds harnesses scoring the same at very different cost per task. Cloudflare's System One demo reached the same answer with 94% fewer tokens, Workday's decision model costs about $20 per million judgments, and Natalie Serrino frames faster tokens as a trade against more tokens for the same energy. Simon Willison's Fable-class brute force qualifies it: for a hard enough goal, spending tokens freely is the method. Sentry's leaner tool set cut tokens by 30%.

Agent memory needs curating

An agent's memory has to be curated, not just accumulated: keep the full history as evidence, but score, prune or re-render what actually reaches the model.

Lovable keeps each agent's task history as an append-only, Git-like log and renders a fresh prompt from it for each model. Steve Yegge warns that agents never delete, so their memory becomes a garbage dump that has to be cut back on purpose. Overcut scores memories from past runs and feeds back only the best. Monaco seeds memory from emails and calls and lets a reflection step promote what agents learn. Lance Martin (Anthropic) explains why: agents write memory greedily inside a session, but memory has to be coherent across sessions, so it needs a separate consolidation pass, dreaming, where Claude reviews transcripts and notes, fixes them and builds new representations such as a wiki; on the Stainless corpus the wiki improved with more dreaming tokens and beat semantic search alone. Stronger models also write and read memory better.

Close the loop

Overcut runs a background retrospective that turns past runs into scored memories. Lovable verifies in two loops, checks within a turn and production and business signals between turns. Brian Kennedy's closing fragment applies it to the judge itself: measure it, and run a second check in shadow mode. Cognition tracks every PR and decision so agents can analyse the record daily and propose improvements to the factory itself.

Less harness, more model

Each model generation absorbs work the last harness had to do, so a harness should shrink to a goal, a computer and the few tools the model can't reach itself, and be rebuilt as models improve.

Philipp Schmid rebuilds his coding harness every six months and asks what is now overhead: the latest is one bash tool, with the model writing its own inline scripts instead of calling file tools. Steve Yegge sees the same arc in software factories: each model generation builds something slightly too big for itself and the next burns it down. Simon Willison's Fable-class models need only a defined goal and the tools to reach it. Lauren Tan qualifies it: deterministic layers such as types, lint and tests still come first. Arsalan Bashir (Sentry) found pre-classifying intent and pre-fetching schemas narrowed what the model saw and had to be recalibrated each release; stripping to fewer, non-overlapping tools made the agent four times faster on 30% fewer tokens, and the model now writes code against APIs. Lance Martin's thousand Fable 5.2 agents got only git, a SQL database and the problem.

Connecting is not answering

Connecting an AI to every source is now cheap, but it does not settle which source answers, so a connection per source produces wrong or conflicting answers unless something decides between them.

George Fraser argues that wiring an assistant to each system of record through MCP fails for data questions because it cannot join across sources. Utkarsh Shrivastava reaches the same problem from inside Netflix: every connector is another way for the agent to choose wrong, two correct connectors gave different viewer counts for one event, and MCP made access cheap without settling who owns the answer. Fraser's fix is one modeled store; Shrivastava's is a platform that gates and arbitrates across domain-owned connectors. Aamir Shakir (Mixedbread) adds the search side: with one MCP server per source the agent has to guess which tool holds the answer, inherits each vendor's weak search, and is only as good as the weakest connector; one prepared search layer raised a bank's answer accuracy from about 40% to 97%. Arsalan Bashir (Sentry) lists how one-tool-per-source agents fail, confusing similar tools, looping on pagination and confidently answering wrong over OLAP warehouses, and organises tools by use case with deterministic code handling the differences.

Decision models

Small decision models that answer a yes/no, a score or a choice in one fast pass take routine decisions off LLMs and people, cheap enough to run on every agent step, every keystroke and every database row.

Michelle Chen's Cloudflare trained its own System One decision model, Clef, in a weekend, so agents stop sending every choice to an LLM. Scott Roberts shows Workday using TypeSafe's Jev the same way: most agent steps are just conditionals, so Jev picks the right UI card as people type, at about $20 per million judgments, and runs as a function inside a DuckDB SQL query, scoring resumes with no embeddings or vector database. Diogo Almeida, who builds Jev, gives the reason: automation needs reliable intelligence, and a reliable decision is a new primitive for software, a fourth logic gate.

Faster tokens
